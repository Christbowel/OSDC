## GHSA-9hj8-73fh-9963 · zip

2026-10-29 · RUST · **HIGH** 7.5 · Pattern: `DOS→RESOURCE_EXHAUSTION`

### Root cause

The vulnerability stemmed from the `zip` crate's legacy decoders (Shrink, Reduce, Implode) attempting to pre-allocate memory based on an unverified `uncompressed_size` value from the ZIP archive metadata. An attacker could provide a maliciously large `uncompressed_size`, leading to excessive memory allocation requests.

### Impact

An attacker could craft a ZIP archive with an extremely large declared uncompressed size, causing the `zip` crate to attempt to allocate a huge amount of memory. This could lead to a 'capacity overflow' panic, an out-of-memory (OOM) error, or a system crash, effectively resulting in a denial of service.

### Key diff

```
--- a/src/legacy/implode.rs
+++ b/src/legacy/implode.rs
@@ -94,7 +94,7 @@ fn hwexplode(
     dst: &mut Vec<u8>,
 ) -> std::io::Result<()> {
     // Pre-allocate capacity
-    dst.reserve(uncomp_len);
+    dst.reserve(uncomp_len.min(crate::legacy::MAX_PREALLOC));
```

### Fix summary

The patch introduces a `MAX_PREALLOC` constant (1MB) to cap the speculative memory pre-allocation. Instead of reserving the full `uncompressed_size` directly, the decoders now reserve `min(uncompressed_size, MAX_PREALLOC)`. This prevents excessive initial memory requests while still allowing larger files to be decoded through geometric buffer growth.

## GHSA-q344-5v34-gm84 · @sylphx/pdf-reader-mcp

2026-10-29 · JavaScript · **HIGH** 7.5 · Pattern: `MISSING_AUTH→ENDPOINT`

### Root cause

The HTTP transport layer for the @sylphx/pdf-reader-mcp package did not enforce API key authentication for the `/mcp` endpoint, even when an `MCP_API_KEY` was configured. This meant that any request to the `/mcp` endpoint would be processed without checking for a valid `X-API-Key` header.

### Impact

An attacker could send unauthenticated requests to the `/mcp` endpoint, bypassing the intended API key protection. This could allow unauthorized access to the PDF processing functionality provided by the service.

## GHSA-q7v9-x93c-xqv3 · zip

2026-10-29 · RUST · **HIGH** 7.5 · Pattern: `DOS→RESOURCE_EXHAUSTION`

### Root cause

The vulnerability stemmed from the zip library's handling of symlink entries during extraction. The `file.size()` method, which reports the uncompressed size of an entry, is attacker-controlled. When extracting a symlink, the library would use this attacker-controlled size to pre-allocate a `Vec` (vector) for the symlink target. An attacker could declare an extremely large uncompressed size for a symlink target, leading to an attempt to allocate a massive amount of memory.

### Impact

An attacker could craft a malicious zip archive that, when extracted, would cause the extracting process to either exhaust available memory and crash (Denial of Service) or abort due to an out-of-memory error. This could make the application or system processing the archive unavailable.

### Key diff

```
--- a/src/read/mod.rs
+++ b/src/read/mod.rs
@@ -395,7 +403,22 @@ impl<R: Read + Seek> ZipArchive<R> {
 
             #[cfg(any(unix, windows))]
             if file.is_symlink() {
-                let mut target = Vec::with_capacity(file.size() as usize);
+                let declared_len = file.size();
+                if declared_len > MAX_SYMLINK_TARGET_LEN {
+                    return Err(invalid!(
+                        "symlink target declares {} bytes, more than the {} byte limit",
+                        declared_len,
+                        MAX_SYMLINK_TARGET_LEN
+                    ));
+                }
+
+                let mut target = Vec::with_capacity(declared_len as usize);
```

### Fix summary

The patch introduces a `MAX_SYMLINK_TARGET_LEN` constant, setting an upper bound of 4096 bytes for symlink target lengths, which aligns with typical platform `PATH_MAX` limits. Before pre-allocating memory for a symlink target, the patch now checks if the declared uncompressed size exceeds this limit. If it does, the extraction process returns an error instead of attempting to allocate an excessive amount of memory.

## GHSA-vpp8-g58w-m8mp · Twisted

2026-10-29 · Python · **HIGH** 7.5 · Pattern: `DOS→RESOURCE_EXHAUSTION`

### Root cause

The Twisted HTTP/2 server was vulnerable to the 'Rapid Reset' attack (CVE-2023-44487) because it did not rate-limit the number of RST_STREAM frames a peer could send. An attacker could rapidly send RST_STREAM frames, causing the server to exhaust its resources by processing and tearing down streams, leading to a denial of service.

### Impact

An unauthenticated remote attacker could send a flood of RST_STREAM frames to the server, causing it to consume excessive CPU and memory resources, ultimately leading to a denial of service where legitimate users could no longer access the service.

## GHSA-qr28-fpjm-wq7f · decode-uri-component

2026-10-29 · JavaScript · **HIGH** 0.0 · Pattern: `DOS→RESOURCE_EXHAUSTION`

### Root cause

The previous implementation of `customDecodeURIComponent` used a quadratic replacement approach. It built a `replaceMap` and then iterated through all keys in the map, performing a global regex replacement on the input string for each key. If there were many distinct percent-encoded runs, each replacement operation would rescan the string, leading to O(N^2) complexity where N is the length of the input string and the number of distinct runs.

### Impact

An attacker could craft a specially malformed URI component with many distinct percent-encoded sequences. Processing such an input would consume excessive CPU resources, leading to a denial of service for applications using this library.

## GHSA-wwpr-jff3-395c · crass

2026-10-29 · Ruby · **MODERATE** 0.0 · Pattern: `DOS→RESOURCE_EXHAUSTION`

### Root cause

The previous implementation of comment consumption used recursion to skip over adjacent comments when the 'preserve_comments' option was false. A large number of consecutive comments in the input CSS could lead to excessive recursion depth, exhausting the Ruby stack.

### Impact

An attacker could craft a CSS input with many adjacent comments, causing the Crass tokenizer to crash with a SystemStackError, leading to a denial of service for applications processing such input.

### Key diff

```
-      if comment_token = consume_comments
-        if @options[:preserve_comments]
-          return comment_token
-        else
-          return consume
-        end
+      loop do
+        return nil if @s.eos?
+        @s.mark
+        comment_token = consume_comments
+        break unless comment_token
+        return comment_token if @options[:preserve_comments]
+      end
```

### Fix summary

The patch refactors the comment consumption logic to use an iterative loop instead of recursion when comments are not being preserved. This prevents a deep call stack from building up, mitigating the SystemStackError.
