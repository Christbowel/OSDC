## GHSA-x44h-65qv-cw74 · praisonaiagents

2026-08-25 · Python · **HIGH** 8.5 · Pattern: `SSRF→INTERNAL_ACCESS`

### Root cause

The original SSRF protection in `_crawl_with_httpx` only validated the initial URL but did not re-validate URLs after redirects. An attacker could provide a URL that initially points to a safe external host but then redirects to an internal or loopback address (e.g., using `127.0.0.1.nip.io` or similar DNS tricks), bypassing the initial check.

### Impact

An attacker could force the application to make requests to internal network resources or cloud metadata endpoints, potentially leading to information disclosure, unauthorized access, or further attacks within the internal network.

### Fix summary

The patch introduces a new function `_is_safe_crawl_url` which performs SSRF checks, including DNS resolution and IP address validation (checking for loopback, private, link-local, multicast, or unspecified IPs). This function is now called for the initial URL and for every redirect target during the crawling process, ensuring all intermediate and final URLs are safe.

## GHSA-7g3p-92qq-8wvh · praisonaiagents

2026-08-25 · Python · **HIGH** 8.2 · Pattern: `MISSING_AUTH→ENDPOINT`

### Root cause

The application's job server lacked authentication enforcement on its routes, allowing unauthorized access. Additionally, the web crawling functionality did not adequately validate URLs, making it vulnerable to SSRF. Finally, the MCP server did not limit the number of active sessions, leading to a potential resource exhaustion DoS.

### Impact

An attacker could execute arbitrary jobs, access internal network resources, or cause a denial of service by exhausting server resources. This could lead to data breaches, unauthorized operations, or service unavailability.

2026-08-25 · Python · **HIGH** 0.0 · Pattern: `SSRF→INTERNAL_ACCESS`

### Root cause

The application's web crawling functionality, intended to prevent Server-Side Request Forgery (SSRF) by validating initial URLs, failed to re-validate URLs after HTTP redirects. This allowed an attacker to provide an initial safe URL that would then redirect to an unsafe internal or private network resource, bypassing the initial security check.

### Impact

An attacker could bypass the existing SSRF protection to access internal network resources, potentially leading to information disclosure, unauthorized access to internal services, or further attacks within the private network.
