## GHSA-2364-jh4q-m9vm · flowise

2026-08-04 · JavaScript · **MODERATE** 0.0 · Pattern: `IDOR→DATA_ACCESS`

### Root cause

The application did not properly validate if the `customerId` or `subscriptionId` provided in API requests belonged to the authenticated user's active organization. This allowed an attacker to request information or perform actions on behalf of other customers/subscriptions by simply changing the ID in the request.

### Impact

An attacker could access sensitive customer or subscription details, such as payment source information, or manipulate subscription quantities and plans for other users without proper authorization.

## GHSA-3769-jgqc-cxm7 · flowise-components

2026-08-04 · JavaScript · **CRITICAL** 0.0 · Pattern: `DESERIALIZATION→RCE`

### Root cause

The application allowed custom `nodeVMOptions` to be merged directly into the `NodeVM` configuration without proper sanitization. This enabled an attacker to override critical security settings like `eval` and `wasm` within the `NodeVM` sandbox, which are designed to prevent arbitrary code execution.

### Impact

An attacker could escape the `NodeVM` sandbox and achieve Remote Code Execution (RCE) on the host system, leading to full compromise of the server.

### Key diff

```
-        const finalNodeVMOptions = { ...defaultNodeVMOptions, ...nodeVMOptions }

+            ...defaultNodeVMOptions,
+            ...nodeVMOptions,
+            require: defaultNodeVMOptions.require,
+            eval: false,
+            wasm: false
+        }
```

### Fix summary

The patch explicitly sets `eval: false` and `wasm: false` in the `finalNodeVMOptions` after merging custom options. This ensures that even if an attacker provides malicious `nodeVMOptions`, these critical security settings cannot be overridden, thereby preventing sandbox escape.

## GHSA-c6xh-wv4j-ppv5 · flowise

2026-08-04 · JavaScript · **HIGH** 0.0 · Pattern: `SSRF→INTERNAL_ACCESS`

### Root cause

The vulnerability existed because the IP address deny list mechanism did not properly normalize IPv4-mapped IPv6 addresses (e.g., ::ffff:192.168.1.1) to their IPv4 equivalents before comparison. An attacker could use these special IPv6 formats to bypass existing IPv4-based deny list rules, allowing access to internal resources that should have been blocked.

### Impact

An attacker could bypass the server-side request forgery (SSRF) protection, enabling them to make requests to internal network resources or other sensitive endpoints that were intended to be blocked by the deny list.

### Key diff

### Fix summary
