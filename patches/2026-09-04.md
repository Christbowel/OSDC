## GHSA-rh53-xvx2-j327 · github.com/openchoreo/openchoreo

2026-09-04 · Go · **CRITICAL** 9.0 · Pattern: `MISSING_AUTH→ENDPOINT`

### Root cause

The internal API listener of the cluster-gateway, which exposes sensitive Kubernetes API proxying capabilities, was configured without client certificate authentication by default. This allowed any caller with network access to the internal API port to interact with the Kubernetes API without presenting any credentials.

### Impact

An attacker with network access to the internal API could disclose data-plane Secrets and perform arbitrary mutations within the Kubernetes cluster, leading to full compromise of the managed clusters.

### Fix summary

The patch introduces a new configuration option, `internal-mtls`, to enable mTLS for the internal API listener. The `TLSConfig` for the internal server is now dynamically built based on this new mTLS setting.

## GHSA-fgmr-7w36-9qfq · github.com/siyuan-note/siyuan/kernel

2026-09-04 · Go · **MODERATE** 5.8 · Pattern: `MISSING_AUTHZ→RESOURCE`

### Root cause

The application's static file serving routes for '/widgets/' and '/plugins/' did not properly enforce access controls. While the REST API had publish-access controls, these static routes bypassed them, allowing unauthenticated or unauthorized users to access files that should have been restricted.

### Impact

An attacker could access sensitive information such as templates, snippets, and export artifacts that were intended to be private or accessible only to authenticated users, potentially leading to further compromise or data leakage.

```
-	widgets.Static("", filepath.Join(util.DataDir, "widgets"))

+		}
+		name, _, _ := strings.Cut(filepath.ToSlash(relativePath), "/")
+		return model.CheckWidgetAccessableByPublishAccess(c, name, model.GetPublishAccess())
	})
```

### Fix summary

The patch introduces a new `registerStaticFileHandlers` function that wraps the static file serving. This function now includes a custom access check callback for '/widgets/' and '/plugins/' routes, ensuring that only users with appropriate roles (e.g., read-only) and publish access permissions can retrieve these resources.

## GHSA-pr7f-p5mw-fc87 · vllm

2026-09-04 · Python · **MODERATE** 0.0 · Pattern: `RACE_CONDITION→TOCTOU`

### Root cause

The original fix for CVE-2025-62164 used `torch.sparse.check_sparse_tensor_invariants()` which relies on a process-global flag. When multiple prompt parts are processed concurrently in a thread-pool, one thread could disable the invariant check while another thread was still relying on it, thus bypassing the security control.

### Impact

An attacker could craft a malicious sparse tensor that, when loaded, could lead to out-of-bounds writes, potentially resulting in arbitrary code execution or denial of service.

### Key diff

```
--- a/vllm/multimodal/media/audio.py
+++ b/vllm/multimodal/media/audio.py
-        with torch.sparse.check_sparse_tensor_invariants():
+        with check_sparse_tensor_invariants_threadsafe():
             tensor = torch.load(buffer, weights_only=True)
```

### Fix summary

The patch introduces a new thread-safe context manager, `check_sparse_tensor_invariants_threadsafe`, which wraps `torch.sparse.check_sparse_tensor_invariants()` with a threading lock. This ensures that only one thread can enable and disable the sparse tensor invariant checks at a time, preventing race conditions during concurrent loading of potentially malicious tensors.
