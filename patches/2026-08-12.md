## GHSA-v7cf-8gh9-gxmj · winter/wn-backend-module

2026-08-12 · PHP · **HIGH** 8.1 · Pattern: `UNSANITIZED_INPUT→XSS`

### Root cause

The application allowed user-supplied custom CSS to be rendered directly into the HTML without proper sanitization. Specifically, the `renderCss()` methods in `BrandSetting.php` and `EditorSetting.php` returned the `$customCss` variable, which could contain malicious HTML/JavaScript, without stripping tags.

### Impact

An attacker with the ability to modify brand settings or editor settings could inject arbitrary JavaScript into the backend, leading to session hijacking, defacement, or further attacks against other authenticated users.

### Key diff

```
-        return $customCss;
+        return strip_tags($customCss);
```

### Fix summary

The patch introduces `strip_tags()` to the return value of the `renderCss()` methods in both `BrandSetting.php` and `EditorSetting.php`. This ensures that any HTML or script tags within the custom CSS are removed before being rendered, preventing XSS.

## GHSA-vgp4-2fc4-qff2 · winter/wn-backend-module

2026-08-12 · PHP · **HIGH** 8.1 · Pattern: `UNSANITIZED_INPUT→XSS`

### Root cause

The application allowed user-supplied custom CSS to be rendered directly into the HTML without proper sanitization. Specifically, the `renderCss()` methods in `BrandSetting.php` and `EditorSetting.php` returned user-controlled CSS content without stripping HTML tags, even if an exception occurred during compilation.

### Impact

An attacker with the ability to modify editor settings could inject malicious JavaScript code, leading to stored Cross-Site Scripting. This could allow them to execute arbitrary scripts in the context of other users' browsers, potentially leading to session hijacking, data theft, or defacement.

### Fix summary

The patch introduces `strip_tags()` to the `renderCss()` methods in both `BrandSetting.php` and `EditorSetting.php`. This ensures that any HTML tags within the custom CSS content, especially in error messages, are removed before being rendered to the browser, preventing XSS.

## GHSA-m7jc-g4rc-jmvh · winter/wn-backend-module

2026-08-12 · PHP · **MODERATE** 5.9 · Pattern: `UNSANITIZED_INPUT→SQL`

### Root cause

The application directly substituted user-controlled values into raw SQL queries using `strtr` without proper sanitization or parameterized queries. Specifically, the `numbersFromAjax` method, which processes user input for number range filters, did not strictly validate or cast input to numeric types, allowing non-numeric strings to be passed into SQL conditions. The `whereRaw` method then executed these interpolated strings, making it vulnerable.

### Impact

An attacker could inject arbitrary SQL into the database queries, potentially leading to unauthorized data access, modification, or deletion within the backend. This could compromise the integrity and confidentiality of the application's data.

### Key diff

```
+                            'filtered' => (float) $scope->value,
+                        ]);
+
+                        $query->whereRaw(DbDongle::parse($sql), $bindings);
                     }

```

### Fix summary

The patch introduces a new `processConditionBindings` method to correctly convert named placeholders in SQL conditions to positional `?` parameters and pass corresponding values as an ordered array of bindings to `whereRaw`. Additionally, the `numbersFromAjax` method now explicitly casts all processed numbers to `float` and strictly checks if input is numeric using `is_numeric` before adding it to the numbers array, preventing non-numeric values from being used in SQL conditions.
