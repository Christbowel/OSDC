## GHSA-8qpj-27x8-pwpq · langflow

2026-10-06 · Python · **CRITICAL** 9.9 · Pattern: `MISSING_AUTHZ→RESOURCE`

### Root cause

The Langflow application's PythonREPLComponent and PythonREPLToolComponent allowed authenticated users to execute arbitrary Python code without proper authorization checks. Although there was a `allow_custom_components` setting, it was not enforced for these specific components, enabling a bypass.

### Impact

An authenticated attacker could execute arbitrary Python code on the server, leading to full system compromise (Remote Code Execution) and potential privilege escalation.

### Fix summary

The patch introduces a new function, `ensure_code_execution_enabled()`, which is called before any user-supplied Python code is executed in the PythonREPLComponent and PythonREPLToolComponent. This function checks the `allow_custom_components` setting and raises an error if code execution is disabled, thereby enforcing the security policy.

## GHSA-v49j-62m6-pgrr · payload

2026-10-06 · JavaScript · **CRITICAL** 9.8 · Pattern: `UNSANITIZED_INPUT→SQL`

### Root cause

The application did not properly validate or sanitize user-controlled input used in sort queries. Specifically, sort parameters were not subject to the same field-read access checks as 'where' clauses, allowing an attacker to inject malicious SQL fragments.

### Impact

An attacker could manipulate sort queries to bypass access controls, potentially exfiltrate sensitive data, or perform other unauthorized database operations.

### Key diff

## GHSA-rm89-rhwj-9j92 · Microsoft.OpenApi.Kiota.Builder

2026-10-06 · C# · **HIGH** 8.8 · Pattern: `UNSANITIZED_INPUT→TEMPLATE`

### Root cause

The vulnerability stemmed from insufficient neutralization of block comment delimiters in user-provided descriptions when generating Java and PHP code. Specifically, the `*/` sequence was simply removed, which could be bypassed by an attacker using `**//` to reform `*/` after the initial removal, allowing them to break out of doc comments and inject arbitrary code.

### Impact

An attacker could inject arbitrary code into the generated Java and PHP client libraries, potentially leading to remote code execution in applications that consume these generated clients.

### Key diff

```
--- a/src/Kiota.Builder/Writers/Java/JavaConventionService.cs
+++ b/src/Kiota.Builder/Writers/Java/JavaConventionService.cs
-            nonAsciiReplaceRegex().Replace(originalDescription.Replace("\\", "/", StringComparison.OrdinalIgnoreCase).Replace("*/", string.Empty, StringComparison.OrdinalIgnoreCase), string.Empty).CleanupXMLString();
+            nonAsciiReplaceRegex().Replace(originalDescription.Replace("\\", "/", StringComparison.OrdinalIgnoreCase), string.Empty).NeutralizeBlockCommentDelimiters().CleanupXMLString();
```

### Fix summary

The patch introduces a new `NeutralizeBlockCommentDelimiters` extension method that replaces `/*` with `//*` and `*/` with `* /`. This ensures that block comment delimiters are properly neutralized and cannot be reformed, preventing attackers from breaking out of generated doc comments.

2026-10-06 · Go · **HIGH** 7.2 · Pattern: `DOS→RESOURCE_EXHAUSTION`

### Root cause

The Web Application Firewall (WAF) had an argument limit feature designed to prevent resource exhaustion from parameter flooding. However, when this limit was reached, arguments beyond the limit were silently dropped without any indication to the WAF's rule engine. This allowed an attacker to prepend a large number of 'filler' parameters, pushing a malicious payload past the argument limit, making it invisible to all subsequent ARGS-targeted rules.

### Impact

An attacker could bypass WAF rules designed to detect malicious input within request arguments (e.g., SQL injection, XSS) by flooding the request with benign parameters, thereby allowing the malicious payload to reach the backend application undetected.

### Fix summary

The patch introduces a new variable, `ARGUMENTS_LIMIT_REACHED`, which is set to '1' whenever the argument limit is hit and arguments are silently dropped. New WAF rules (200004 and 200005) are added to explicitly deny requests when this variable is set, ensuring that requests exceeding the argument limit are rejected instead of silently dropping arguments.

## GHSA-vc4h-q48j-5hcx · payload

2026-10-06 · JavaScript · **CRITICAL** 0.0 · Pattern: `MISSING_AUTHZ→RESOURCE`

### Root cause

The vulnerability stemmed from an oversight in how Payload handled document duplication, specifically for collections with authentication enabled. When duplicating an authenticated document, the system did not properly enforce field-level access control, allowing fields that should have been restricted to be copied over to the new document.

### Impact

An attacker could bypass field-level access controls on authenticated collections by duplicating existing documents. This could lead to unauthorized disclosure or modification of sensitive data that would otherwise be protected by access rules.

## GHSA-w5f4-fx9m-m4q7 · Microsoft.Native.Quic.MsQuic.OpenSSL

2026-10-06 · C# · **CRITICAL** 0.0 · Pattern: `MISSING_VERIFICATION→SIGNATURE`

### Root cause

The MsQuic client-side TLS implementation did not properly validate server certificates. Specifically, it only used the SNI (Server Name Indication) for host name matching, but did not explicitly configure OpenSSL's `X509_VERIFY_PARAM` to perform robust host name validation against the certificate's Subject Alternative Name (SAN) or Common Name (CN) fields. This allowed an attacker to present a valid certificate for a different domain, which would still be accepted by the client.

### Impact

An attacker could perform a Man-in-the-Middle (MitM) attack by presenting a valid certificate for a different domain, tricking the client into connecting to a malicious server while believing it is communicating with the legitimate one. This could lead to eavesdropping or data tampering.
