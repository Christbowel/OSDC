## GHSA-2h44-8472-frjj · @zereight/mcp-gitlab

2026-09-15 · JavaScript · **CRITICAL** 9.6 · Pattern: `SSRF→INTERNAL_ACCESS`

### Root cause

The application allowed dynamic GitLab API URLs to be provided via an HTTP header (X-GitLab-API-URL). While there was a `resolveTrustedGitLabApiUrl` function intended to validate these URLs, the error handling around its invocation was too broad, catching all exceptions and preventing the application from properly rejecting untrusted or malformed URLs. This allowed an attacker to bypass the intended host restrictions.

### Impact

An attacker could craft a malicious X-GitLab-API-URL header to force the server to make requests to arbitrary internal or external systems, potentially accessing sensitive internal resources or performing actions on other services.

### Key diff

```
--- a/index.ts
+++ b/index.ts
@@ -13289,8 +13292,9 @@ async function startStreamableHTTPServer(): Promise<void> {
     if (ENABLE_DYNAMIC_API_URL && dynamicApiUrl) {
       try {
         apiUrl = resolveTrustedGitLabApiUrl(dynamicApiUrl);
-      } catch {
-        logger.warn(`Invalid X-GitLab-API-URL provided: ${dynamicApiUrl}. Auth will fail.`);
+      } catch (error) {
+        const reason = error instanceof Error ? error.message : "Invalid X-GitLab-API-URL";
+        logger.warn(`Invalid X-GitLab-API-URL provided: ${dynamicApiUrl}. ${reason}`);
         return null; // Reject if URL is malformed or not allowed
       }
     }
```

### Fix summary

The patch modifies the error handling blocks where `resolveTrustedGitLabApiUrl` is called. Instead of a generic `catch` block, the specific error message from the validation function is now captured and included in the warning log or HTTP response. This ensures that invalid or untrusted URLs are properly rejected, preventing the SSRF.

## GHSA-vmp7-252j-cwp7 · @zereight/mcp-gitlab

2026-09-15 · JavaScript · **CRITICAL** 9.6 · Pattern: `SSRF→INTERNAL_ACCESS`

### Root cause

The application did not properly validate the 'Host' and 'Origin' headers for incoming requests to the /mcp endpoint. This allowed an attacker to use DNS rebinding techniques to trick a browser into making requests to the local server, bypassing typical same-origin policy protections.

### Impact

An attacker could potentially bypass network restrictions and access internal services or data on the server running the application, leading to unauthorized data access or remote code execution if other vulnerabilities exist in those internal services.

### Key diff

```

### Fix summary

The patch introduces new middleware, `requireMcpHostAndOrigin`, which validates the 'Host' and 'Origin' headers against a list of allowed hosts and origins, including special handling for loopback addresses. This prevents requests with unapproved host/origin headers from reaching the MCP transport.

## GHSA-9998-894r-fwvr · org.http4s:http4s-ember-core_3

2026-09-15 · Java · **HIGH** 8.7 · Pattern: `UNSANITIZED_INPUT→HEADER`

### Root cause

The Http4s Ember parser incorrectly handled the Transfer-Encoding header. It used the platform's default charset (UTF-8) for decoding header values, which could lead to multi-byte sequences being interpreted as single non-ASCII codepoints. This, combined with a loose check for 'chunked' using `contains` and `equalsIgnoreCase`, allowed attackers to craft ambiguous Transfer-Encoding headers that different proxies/servers might interpret differently, leading to request smuggling.

### Impact

An attacker could bypass security controls, access unauthorized resources, or poison web caches by manipulating the interpretation of HTTP requests between a frontend proxy and the Http4s Ember server. This could lead to various attacks, including cache poisoning, firewall bypass, and potentially remote code execution if combined with other vulnerabilities.

### Key diff

```
-            val hValue = new String(message, start, idx - start - 1).trim
+            val hValue = new String(message, start, idx - start - 1, StandardCharsets.ISO_8859_1).trim
...
-              chunked = hValue.contains(chunkedS)
+              val codings = hValue.split(',')
+              if (codings.isEmpty || codings.exists(c => !c.trim.equalsIgnoreCase(chunkedS)))
+                progress = Progress.Errored(UnsupportedTransferEncoding)
+              else
+                chunked = true
```

### Fix summary

The patch introduces a more robust parsing mechanism for HTTP headers. It explicitly decodes header values using ISO-8859-1 charset, as per RFC 9110, and strictly validates Transfer-Encoding headers. Only 'chunked' is supported, and any other transfer coding or malformed value now results in an error, preventing ambiguity.

### Key diff

### Fix summary

## GHSA-8f3q-3jmv-7prw · org.http4s:http4s-ember-core_2.13

2026-09-15 · Java · **HIGH** 7.5 · Pattern: `DOS→RESOURCE_EXHAUSTION`

### Root cause

The Http4s Ember HTTP/2 implementation used unbounded queues for outbound HTTP/2 frames in both client and server components. This meant there was no limit to the number of frames that could be queued, allowing an attacker to continuously send data without the server or client being able to process it fast enough.

### Impact

An attacker could exhaust system memory by continuously sending HTTP/2 frames, leading to a denial of service for the application or server.

### Key diff

```
-        queue <- cats.effect.std.Queue.unbounded[F, Chunk[H2Frame]] // TODO revisit
+        queue <- cats.effect.std.Queue.bounded[F, Chunk[H2Frame]](128)
```

### Fix summary

The patch replaces the unbounded queues with bounded queues, setting a maximum capacity of 128 frames. This prevents an attacker from overwhelming the system by queuing an excessive number of frames.

## GHSA-9vwc-pc8p-253q · org.http4s:http4s-ember-core_3

2026-09-15 · Java · **HIGH** 7.5 · Pattern: `DOS→RESOURCE_EXHAUSTION`

### Root cause

The Http4s Ember HTTP/2 server implementation did not properly enforce the SETTINGS_MAX_CONCURRENT_STREAMS setting. This allowed a malicious client to open an excessive number of concurrent streams, leading to resource exhaustion.

### Impact

An attacker could exhaust server resources by opening too many concurrent HTTP/2 streams, causing the server to become unresponsive or crash, thereby denying service to legitimate users.

### Key diff

```

@@ -326,8 +337,11 @@ private[ember] object H2Server {

+      maxStreams <- Resource.eval(

+      )

+      _ <- processCreatedStreams(h2, maxStreams).background

## GHSA-rf68-8gjr-36q7 · github.com/nezhahq/nezha

2026-09-15 · Go · **LOW** 0.0 · Pattern: `UNSANITIZED_INPUT→HEADER`

### Root cause

The application's OAuth2 redirect URL generation logic, specifically when the 'dashboard_host' configuration was empty, allowed the 'Host' header from the incoming request to be used directly. This created a vulnerability where an attacker could manipulate the 'Host' header to redirect users to an arbitrary malicious domain after successful authentication with the OAuth provider.

### Impact

An attacker could perform phishing attacks by redirecting authenticated users to a controlled malicious site, potentially stealing their session tokens or tricking them into revealing credentials on a look-alike page.
