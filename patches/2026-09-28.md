## GHSA-58mr-gqgx-xq4g · fast-uri

2026-09-28 · JavaScript · **HIGH** 7.5 · Pattern: `TYPE_CONFUSION→BYPASS`

### Root cause

The vulnerability stemmed from an incorrect assumption in `fast-uri`'s host parsing logic. It treated any host string starting with '[' and ending with ']' as a valid IP literal (e.g., IPv6 address), bypassing further validation. However, an unclosed bracket, like `[example.com`, would also satisfy this check, leading to it being incorrectly processed as an IP literal rather than a regular domain name.

### Impact

An attacker could craft a URI with a malformed host (e.g., `http://[example.com`) that would be parsed differently by `fast-uri` compared to other URI parsers. This discrepancy could lead to host confusion, potentially bypassing security checks, allowing access to unintended resources, or facilitating SSRF-like attacks if the URI is used in a context where host validation is critical.

### Fix summary

The patch introduces a new helper function `isIPLiteral` which explicitly checks if a host string starts with '[' AND ends with ']'. This function is then used consistently throughout the code where host validation occurs, ensuring that only properly bracketed IP literals are treated as such, and malformed strings with unclosed brackets are correctly processed as regular domain names.

### Root cause

The `fast-uri` library's `serialize` function did not properly validate the `port` component of a URI. It directly appended the `port` value to the URI string without ensuring it contained only digits, allowing non-numeric characters to be injected.

### Impact

An attacker could inject arbitrary characters into the authority component of a URI, potentially leading to misinterpretation by downstream systems, bypass of security checks, or other unexpected behavior when the URI is processed or displayed.

## GHSA-rpw4-54j3-4h4q · ip-address

2026-09-28 · JavaScript · **MODERATE** 0.0 · Pattern: `SSRF→INTERNAL_ACCESS`

### Root cause

The `isLinkLocal()` method in the `ip-address` library incorrectly identified link-local IPv6 addresses. It only recognized addresses within the `fe80::/64` subnet, rather than the broader `fe80::/10` range as defined by RFC 4291. This narrow check allowed other valid link-local addresses outside of `fe80::/64` to be misclassified as non-link-local.

### Impact

An attacker could bypass trust boundaries or SSRF protections that rely on `isLinkLocal()` to prevent connections to on-link hosts. This could lead to unauthorized access to internal services or information disclosure from devices on the local network.
