## GHSA-5q7h-w9jf-cx97 · github.com/chainguard-dev/kaniko

2026-11-05 · Go · **CRITICAL** 9.3 · Pattern: `UNSANITIZED_INPUT→REGEX`

### Root cause

The original regular expression `acrRE` used to identify Azure Container Registry (ACR) hosts was unanchored. This allowed an attacker to craft a malicious hostname like `evil.azurecr.io.attacker.com` which would be incorrectly identified as an ACR host, leading to the leakage of sensitive Azure (Entra ID) access tokens.

### Impact

An attacker could trick Kaniko into sending Azure (Entra ID) access tokens to a malicious lookalike registry, potentially compromising the victim's Azure resources and allowing unauthorized access to their container images and other cloud services.

### Key diff

```
-var acrRE = regexp.MustCompile(`\.azurecr\.(?:io|cn|de|us)$`)
+var acrHostRE = regexp.MustCompile(`^(?:[a-z0-9](?:[a-z0-9-]{0,61}[a-z0-9])?\.)+azurecr\.(?:io|cn|de|us)$`)
 // ...
-func isACRRegistry(input string) bool {
-   return acrRE.MatchString(input) || input == mcrHostname
+func isACRRegistry(input string) bool {
+   serverURL, err := url.Parse("https://" + input)
+   if err != nil || serverURL.Host != input {
+      return false
+   }
+   // ... additional port and hostname validation ...
+   host := serverURL.Hostname()
+   return host == mcrHostname || acrHostRE.MatchString(host)
}
```

### Fix summary

The patch introduces a new, anchored regular expression `acrHostRE` that strictly validates ACR hostnames. It also adds robust parsing and validation for the entire `serverURL` input, ensuring that only well-formed and legitimate ACR or MCR hostnames (including port validation) are recognized before attempting to retrieve credentials. Additionally, it now reports 'credentials not found' for non-ACR hosts instead of a generic error.

## GHSA-64vx-6h2c-rjh7 · banks

2026-11-05 · Python · **HIGH** 7.5 · Pattern: `UNSANITIZED_INPUT→COMMAND`

### Root cause

The `CompletionExtension` class used `importlib.import_module` to dynamically load Python modules and functions based on an `import_path` provided by a `Tool` object. This `Tool.import_path` could be controlled by an attacker, allowing them to specify arbitrary modules and functions to be imported and executed, leading to remote code execution.

### Impact

An attacker could execute arbitrary Python code on the server where the 'banks' application is running, potentially leading to full system compromise, data exfiltration, or denial of service.

### Key diff

```
--- a/src/banks/extensions/completion.py
+++ b/src/banks/extensions/completion.py
-                module = importlib.import_module(module_name)
-                return getattr(module, func_name)
+        if name not in self._callable_registry:
+            msg = f"Function {name!r} is not registered"
+            raise ValueError(msg)
+        return self._callable_registry[name]
```

### Fix summary

The patch removes the use of `importlib.import_module` and introduces a `_callable_registry` within the `CompletionExtension` class. Tools must now be explicitly registered with this registry using the `register_callable` method, ensuring that only pre-approved functions can be invoked. Additionally, the `import_path` is excluded from tool dictionaries sent to external models.
