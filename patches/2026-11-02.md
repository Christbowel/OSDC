## GHSA-f9j6-8p6x-r9j6 · @sd-jwt/core

2026-11-02 · JavaScript · **HIGH** 0.0 · Pattern: `MISSING_VERIFICATION→SIGNATURE`

### Root cause

The library was vulnerable to silently dropping tampered disclosures instead of rejecting them. This was due to using `JSON.parse(base64urlDecode(s))` which is lenient and can parse malformed JSON, allowing attackers to craft disclosures that would be ignored rather than causing an error during verification. Additionally, reserved fields in the payload were not properly validated, and the `_sd_alg` parameter was not strictly checked against known algorithms.

### Impact

An attacker could craft a malicious SD-JWT where certain disclosures are silently ignored, potentially leading to a bypass of security checks or misinterpretation of the presented claims, without the verifier being aware of the tampering.

### Key diff

```
-	const item = JSON.parse(base64urlDecode(s)) as DisclosureData<T>;
+	const item = decodeBase64urlJsonStrict<DisclosureData<T>>(
+	  s,
+	  'Invalid disclosure data',
+	);
```

### Fix summary

The patch introduces `decodeBase64urlJsonStrict` for parsing base64url-encoded JSON, which strictly validates the input and throws an error for malformed JSON. It also adds validation for reserved fields in the payload and ensures that the `_sd_alg` parameter is a recognized IANA hash algorithm, preventing silent dropping of invalid disclosures or payloads.

## GHSA-j656-3hf2-fvjc · @bytebase/dbhub

2026-11-02 · JavaScript · **MODERATE** 0.0 · Pattern: `UNSANITIZED_INPUT→SQL`

### Root cause

The previous read-only SQL validation mechanism relied on keyword classification and comment parsing, which could be bypassed by specific MySQL/MariaDB comment interpretations (e.g., `--`-hidden statements) or function-based writes. This allowed DML statements to execute even when the system was configured for read-only access.

### Impact

An attacker could execute arbitrary DML (Data Manipulation Language) statements, such as INSERT, UPDATE, DELETE, or REPLACE, against the database, even when the application intended to restrict operations to read-only queries. This could lead to data modification, corruption, or unauthorized data deletion.

### Key diff

```
Before:
    const conn = await this.pool.getConnection();
    try {
      // Apply maxRows limit to SELECT queries if specified

After:
    const conn = await this.pool.getConnection();
    try {
      if (options.readonly) {
        await conn.query("START TRANSACTION READ ONLY");
      }
```

### Fix summary

The patch introduces an engine-level read-only transaction for MySQL, MariaDB, and PostgreSQL, and `PRAGMA query_only=ON` for SQLite, when the `options.readonly` flag is set. This ensures that the database engine itself rejects any DML write operations, providing a robust backstop even if the keyword classifier or comment parser is bypassed. It also includes rollback logic for error handling.
