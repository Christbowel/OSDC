## GHSA-w2x5-gv52-9ccv · org.sakaiproject.rubrics:rubrics-impl

2026-08-24 · Java · **HIGH** 8.7 · Pattern: `UNSANITIZED_INPUT→XSS`

### Root cause

The application did not properly sanitize user-supplied input before storing it in the database and later rendering it in the UI. Specifically, fields like 'description' and 'comments' in Rubric, Criterion, Rating, and Evaluation objects were vulnerable.

### Impact

An attacker could inject malicious scripts into the application, which would then be executed in the browsers of other users viewing the affected content. This could lead to session hijacking, defacement, or redirection to malicious sites.

## GHSA-3gjw-f78c-vvpw · tokio-postgres

2026-08-24 · RUST · **MODERATE** 0.0 · Pattern: `DOS→RESOURCE_EXHAUSTION`

### Root cause

The application did not validate that the number of fields in a DataRow message received from the PostgreSQL server matched the expected number of columns defined in the Statement. This mismatch could lead to out-of-bounds indexing when accessing column data.

### Impact

An attacker controlling the PostgreSQL server (or an intermediary) could send a malformed DataRow message, causing the client application to panic and crash, leading to a denial of service.

## GHSA-rgqc-3x5p-6gwg · postgres-protocol

2026-08-24 · RUST · **MODERATE** 0.0 · Pattern: `DOS→RESOURCE_EXHAUSTION`

### Root cause

The vulnerability existed because the `split_at` method in Rust, when used with an attacker-controlled length, could panic if the requested length exceeded the buffer's actual size. This allowed a malicious PostgreSQL server to send a malformed `hstore` value with an oversized length, triggering a panic in the client.

### Impact

### Fix summary

The patch replaces `split_at` with `split_at_checked` when processing key and value lengths for `hstore` entries. `split_at_checked` returns an `Option` which is then unwrapped with `ok_or`, converting a potential panic into a recoverable error if the length is invalid.

## GHSA-w67g-5rqw-f597 · github.com/gorilla/websocket

2026-08-24 · Go · **MODERATE** 0.0 · Pattern: `WEAK_CRYPTO→RANDOM`

### Root cause

The Gorilla WebSocket library used `math/rand` for generating WebSocket mask keys. This package is a cryptographically weak pseudo-random number generator (PRNG) and is not suitable for security-sensitive operations, making the mask keys predictable.

### Impact

An attacker could potentially predict the mask keys used in WebSocket communication, which might allow them to bypass security measures or manipulate data streams if other vulnerabilities are present that rely on the unpredictability of these keys.
