## GHSA-h8m9-jgf8-vwvp · prowler-cloud

2026-09-11 · Python · **CRITICAL** 9.6 · Pattern: `MISSING_VERIFICATION→SIGNATURE`

### Root cause

The system allowed any tenant to claim any email domain in its SAML configuration without proper verification. Specifically, the SAML authentication process did not adequately validate that the email domain asserted in the SAML response matched the tenant whose ACS endpoint was being used, nor did it verify if the user was already a member of that tenant. This allowed an attacker to potentially link an existing user's account to a malicious tenant's SAML configuration.

### Impact

An attacker could perform cross-tenant account takeover, gaining unauthorized access to user accounts in other tenants by manipulating SAML assertions and exploiting the lack of domain validation during the account linking process.

## GHSA-rqx4-3f6q-3x2v · @mockoon/cli

2026-09-11 · JavaScript · **HIGH** 8.8 · Pattern: `MISSING_AUTH→ENDPOINT`

### Root cause

The application exposed an administrative API without any authentication by default. Additionally, it used a wildcard CORS policy ('Access-Control-Allow-Origin: *') for this unauthenticated API, allowing any origin to make requests. This combination made it possible for an attacker to interact with the admin API from any website.

### Impact

An attacker could hijack mock states, steal secrets (e.g., environment variables, transaction logs which might contain sensitive data), and potentially manipulate the application's behavior by setting arbitrary environment variables (though mitigated by a prefix, it was still a risk if the prefix was empty).

The previous check `startsWith()` was insufficient as it could be bypassed by paths like `/path/to/base/../secret` which would still start with `/path/to/base` but resolve outside.

## GHSA-992q-9gwp-7r79 · github.com/zitadel/zitadel

2026-09-11 · Go · **MODERATE** 4.8 · Pattern: `MISSING_VERIFICATION→SIGNATURE`

### Root cause

The ZITADEL auto-linking feature, which links external identity provider (IdP) accounts to existing ZITADEL accounts based on email, did not verify if the email address provided by the IdP was actually verified by the IdP itself. This allowed an attacker to register with an IdP using an unverified email address belonging to another ZITADEL user and then link to that user's ZITADEL account.

### Impact

An attacker could take over a ZITADEL account by registering with an external IdP using the victim's email address (even if unverified by the IdP) and then using the auto-linking feature to gain access to the victim's ZITADEL account.
