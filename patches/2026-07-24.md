## GHSA-7g7r-gx96-252g · app-builder-lib

2026-07-24 · JavaScript · **HIGH** 7.8 · Pattern: `UNSANITIZED_INPUT→COMMAND`

### Root cause

The vulnerability stemmed from the `electron-updater` package using `execWine` to run the uninstaller without proper path sanitization or environment control. This allowed an attacker to manipulate the search path for executables, leading to the execution of a malicious binary instead of the legitimate uninstaller.

### Impact

An attacker could achieve arbitrary code execution by placing a malicious executable in a predictable location within the search path, which would then be executed with the privileges of the application during the uninstallation process.

```
+      await wineVm.exec(installerPath, [], { env: { __COMPAT_LAYER: "RunAsInvoker" } })
     }

```

### Fix summary

The patch replaces the direct use of `execWine` with `WineVmManager.exec`, which provides a more controlled and isolated environment for executing Wine commands. It also removes direct calls to `getPath7za` and `exec` in favor of encapsulated utility functions, reducing the risk of path manipulation.

## GHSA-4w2j-m93h-cj5j · quinn-proto

2026-07-24 · RUST · **HIGH** 7.5 · Pattern: `DOS→RESOURCE_EXHAUSTION`

### Root cause

The `quinn-proto` library, used for QUIC connections, did not properly limit the number of out-of-order stream frames that could be buffered for reassembly. An attacker could send many small, non-contiguous frames, causing the `Assembler` to store an unbounded number of `Buffer` chunks, leading to excessive memory consumption.

### Impact

An attacker could send specially crafted QUIC stream frames to a server or client using `quinn-proto`, causing it to consume an ever-increasing amount of memory. This would lead to a denial-of-service (DoS) condition as the application or system runs out of memory and crashes or becomes unresponsive.

### Key diff

```
--- a/quinn-proto/src/connection/assembler.rs
+++ b/quinn-proto/src/connection/assembler.rs
@@ -209,6 +214,10 @@ impl Assembler {
             self.defragment();
             // ngtcp2 uses a threshold of 4000 -- try to be a little more conservative?
             if self.data.len() > 1024 {
                 return Err(TooManyChunks);
             }
         }
+
         Ok(())
     }
```

### Fix summary

The patch introduces a new error type `TooManyChunks` and modifies the `insert` method in the `Assembler` to return a `Result`. After defragmentation, if the number of buffered data chunks (`self.data.len()`) exceeds a threshold (1024), an `Err(TooManyChunks)` is returned, preventing unbounded growth of the buffer.

## GHSA-j5g9-f88f-gfj3 · httplib2

2026-07-24 · Python · **HIGH** 7.5 · Pattern: `DOS→RESOURCE_EXHAUSTION`

### Root cause

The httplib2 library previously decompressed gzipped or deflated content without any limits on the output size. An attacker could send a specially crafted, small compressed payload that, when decompressed, expands into an extremely large amount of data, consuming excessive memory or CPU resources.

### Impact

An attacker could trigger a Denial of Service (DoS) condition on a system using httplib2 to process HTTP responses, leading to resource exhaustion, application crashes, or unresponsiveness.

## GHSA-chx6-hx7r-mcp5 · react-router

2026-07-24 · JavaScript · **HIGH** 0.0 · Pattern: `DOS→RESOURCE_EXHAUSTION`

### Root cause

The vulnerability stemmed from inefficient route matching logic in React Router. When processing manifest requests, especially those with a 'paths' query parameter, the server-side code would generate all ancestor paths for each requested path. This process involved string splitting and joining in a loop, leading to a significant performance degradation and resource exhaustion when a large number of paths or very long paths were provided in the URL.

### Impact

An unauthenticated attacker could craft a malicious URL with a long 'paths' query parameter, causing the server to perform excessive computations. This would lead to a denial of service, making the application unresponsive or crashing the server.

## GHSA-g357-x5c3-c72p · liquidjs

2026-07-24 · JavaScript · **HIGH** 0.0 · Pattern: `DOS→RESOURCE_EXHAUSTION`

### Root cause

The `pop` filter in LiquidJS did not account for the memory usage of the array it processed, unlike other array-manipulating filters. This oversight allowed an attacker to craft an input that would consume excessive memory without being limited by the `memoryLimit` configuration.

### Impact

An attacker could provide a large array to the `pop` filter, leading to uncontrolled memory consumption and potentially a denial of service for the application hosting the LiquidJS template engine.
