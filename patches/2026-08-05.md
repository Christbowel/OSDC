## GHSA-jm7p-cc5g-qwxx · electron

2026-08-05 · JavaScript · **MODERATE** 6.3 · Pattern: `RACE_CONDITION→TOCTOU`

### Root cause

The vulnerability existed because the code signature check for the parent process relied on the Process ID (PID). PIDs can be reused by the operating system or a malicious process could exec() into a different image after the initial PID lookup, allowing an attacker to spoof the parent process's identity and bypass security checks.

### Impact

An attacker could bypass security checks that rely on verifying the parent process's code signature. This could allow a malicious process to masquerade as a legitimate parent, potentially enabling it to run sandboxed applications with custom arguments, which is normally forbidden on macOS.

### Key diff

```
--- a/shell/common/mac/codesign_util.cc
+++ b/shell/common/mac/codesign_util.cc
-bool ProcessSignatureIsSameWithCurrentApp(pid_t pid) {
+bool ProcessSignatureIsSameWithCurrentApp(audit_token_t audit_token) {
...
-  const void* attribute_keys[] = {kSecGuestAttributePid};
-  const void* attribute_values[] = {process_cf.get()};
+  const void* attribute_keys[] = {kSecGuestAttributeAudit};
+  const void* attribute_values[] = {audit_token_cf.get()};
```

### Fix summary

The patch changes the parent process verification mechanism from using a PID to using an audit token. Audit tokens are bound to a specific process instance and incorporate a per-exec version, making them resistant to PID reuse and exec() spoofing. The audit token is retrieved early in the child process's startup.

## GHSA-9pf5-hg6p-4pwp · electron

2026-08-05 · JavaScript · **MODERATE** 5.9 · Pattern: `MISSING_AUTHZ→RESOURCE`

### Root cause

The permission check handler incorrectly used the main frame's origin for permission checks, even when the request originated from an iframe. This allowed an iframe with a different origin to bypass permission restrictions by inheriting the permissions of its main frame.

### Impact

An attacker could embed a malicious iframe that, despite having a different origin, could request and potentially gain access to sensitive resources like media devices (camera/microphone) or serial ports, which should have been restricted by its own origin policy.

### Key diff

```
--- a/shell/browser/web_contents_permission_helper.cc
+++ b/shell/browser/web_contents_permission_helper.cc
-  auto* rfh = web_contents_->GetPrimaryMainFrame();
-  auto origin = web_contents_->GetLastCommittedURL();
-  return permission_manager->CheckPermissionWithDetails(permission, rfh, origin,
-                                                        std::move(details));
+  auto origin = requesting_frame->GetLastCommittedOrigin().GetURL();
+  return permission_manager->CheckPermissionWithDetails(
+      permission, requesting_frame, origin, std::move(details));
```

### Fix summary

The patch modifies the permission checking functions to explicitly pass and use the `requesting_frame` (RenderFrameHost) and its `GetLastCommittedOrigin()` for permission checks. This ensures that permissions are evaluated based on the actual origin of the frame making the request, rather than always defaulting to the main frame's origin.

## GHSA-pfmc-3mgc-p6fp · electron

2026-08-05 · JavaScript · **LOW** 3.9 · Pattern: `INTEGER_OVERFLOW→BOUNDARY`

### Root cause

The Electron off-screen rendering component trusted geometry information (e.g., content_rect, pixel_size) received from the potentially malicious GPU process over Mojo. This information was used to size bitmaps and canvases backed by shared memory without proper validation against the actual shared memory mapping size, leading to potential out-of-bounds reads.

### Impact

An attacker controlling the GPU process could craft malicious geometry data to cause the browser process to read past the bounds of a shared memory mapping. This could lead to information disclosure (reading sensitive data from adjacent memory) or a crash (denial of service).
