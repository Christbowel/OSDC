## GHSA-2956-977x-2w3r · flyto-core

2026-07-30 · Python · **CRITICAL** 10.0 · Pattern: `PATH_TRAVERSAL→FILE_WRITE`

### Root cause

The application allowed an attacker to control both the target file path and its base directory when writing files. The existing path traversal check was ineffective because it validated the output path against a caller-supplied output directory, which an attacker could manipulate to bypass the check and write files outside the intended sandbox.

### Impact

An attacker could write arbitrary files to any location on the file system where the application has write permissions, potentially leading to remote code execution, data corruption, or denial of service.

### Key diff

```
-    base_real = os.path.realpath(output_dir)
-    target_real = os.path.realpath(output_path)
-    if os.path.commonpath([base_real, target_real]) != base_real:
-        raise Exception('Invalid file path')
+    try:
+        target_real = validate_path_with_env_config(output_path)
+    except PathTraversalError as e:
+        raise ModuleError(str(e), code="PATH_TRAVERSAL")
```

### Fix summary

The patch removes the ineffective local path traversal check and replaces it with a centralized `validate_path_with_env_config` utility function. This new function enforces that all file write operations are confined to a secure, operator-configured sandbox directory (`FLYTO_SANDBOX_DIR`), preventing path traversal attacks.

## GHSA-hr7p-wg7r-hg9m · flyto-core

2026-07-30 · Python · **HIGH** 8.6 · Pattern: `UNCLASSIFIED`

### Root cause

The workflow engine allowed interpolation of environment variables using `${env.VAR}` syntax in step parameters. This interpolation occurred before the module's denylist for `env.get` was applied, effectively bypassing the security control intended to prevent reading arbitrary host environment variables.

### Impact

An attacker could craft input that, when processed by the workflow engine, would read and exfiltrate any environment variable from the host system, potentially leading to the disclosure of sensitive secrets or credentials.

### Key diff

+# Environment-variable interpolation policy
+# ---------------------------------------------------------------------------
+#
+# The workflow engine expands ${env.VAR} in step parameters. That is the exact
+# capability the `env.get` module denylist exists to block (reading arbitrary
+# host env vars = secret exfil). Interpolation happens in the engine BEFORE the
+# module chokepoint, so denylisting `env.get` alone does not stop it

+#

## GHSA-4mrv-5p47-p938 · msgpack

2026-07-30 · Ruby · **LOW** 0.0 · Pattern: `USE_AFTER_FREE→MEMORY`

### Root cause

The `MessagePack::Buffer#clear` method, specifically the `_msgpack_buffer_shift_chunk` function, did not properly reset all internal pointers related to memory management after clearing the buffer. This left `rmem_end`, `rmem_last`, and `rmem_owner` pointing to potentially freed or invalid memory.

### Impact

An attacker could potentially achieve cross-buffer disclosure, meaning data from one buffer could be inadvertently exposed or accessed when another buffer reuses the freed memory region, leading to information leakage.

### Key diff

```
--- a/ext/msgpack/buffer.c
+++ b/ext/msgpack/buffer.c
@@ -134,6 +134,9 @@ bool _msgpack_buffer_shift_chunk(msgpack_buffer_t* b)
          * because head should be always available */
         b->tail_buffer_end = NULL;
         b->read_buffer = NULL;
+        b->rmem_end = NULL;
+        b->rmem_last = NULL;
+        b->rmem_owner = NULL;
         return false;
     }
```

### Fix summary

The patch addresses the vulnerability by explicitly setting `b->rmem_end`, `b->rmem_last`, and `b->rmem_owner` to `NULL` within the `_msgpack_buffer_shift_chunk` function when the buffer is cleared. This ensures that all relevant memory pointers are properly invalidated, preventing use-after-free scenarios.
